# 回放落点实验室（seeklab）

同一张 DASH `SegmentTimeline` 的两套落点实现，数据完全相同，只有查找策略不同：

| | 旧路径（复刻 dash.js 5.3.0） | 新路径（本项目） |
|---|---|---|
| 查找 | 每次 seek 从第一个 S 元素重新线性展开 `@r`（含负 `@r`）并逐片比对，O(n) | 时间轴构建时一次性展平（含空档），之后整数刻度二分查找，O(log n) |
| 空档 | `GapController` 每 250 ms 轮询一次才发现落点，多次调度周期叠加 | 同一次查找内直接返回空档后第一片，落在其起点 +0.001 s |
| 结果 | 两者在 21867 个探测点上逐字段一致（落点秒数 / 序号 / 编号 / 起点 / 时长 / 媒体时间 / 地址 / 后续片序列） | 同左 |

没有替换播放框架，也没有引入 shaka-player / hls.js / video.js：这是这套回放自己的时间轴查找逻辑。


## 测量协议（与要求一致）

1. 先在同一时间轴别的位置点一次，**不计时**（预热）；
2. 再执行目标查找，连量三次；
3. 取三次中位数，与限值比较。

预览页上「量空档落点 ×3」「量 40 次连拖 ×3」按钮即此协议；页面直接显示**这次落点的秒数**和**松手到落点的毫秒数**。

本机实测（Node 22，数字随机器浮动，限值有百倍余量）：

| 项目 | 限值 | 新路径中位 | 旧路径中位（同机同协议） |
|---|---|---|---|
| 拖到 3601 s 的空档落点 | < 2 ms | ≈ 0.01 ms | ≈ 0.3–2 ms |
| 后半段 40 次连拖（每次落点片 + 后 12 片） | < 200 ms | ≈ 1 ms（整批 40 次） | ≈ 10–16 ms（整批） |

旧播放器里观察到的 10.9 s / 15.1 s 不是单次数组扫描的耗时，而是「250 ms 轮询发现空档 → 线性扫描找不到片 → 调度空转 → 下一轮询再试」多个周期叠加（见 `src/streaming/controllers/GapController.js` 的 `checkInterval: 250` 与 `TimelineSegmentsGetter._iterateSegments`）。新路径在一次查找内同时完成定位与空档跳转，轮询空转被整体消除。

## 设计要点

- 展平时显式保存空档（gap）对象，二分只在真实片上进行；落入空档时返回空档后第一片并给出 `landedTime = 该片起点 + 0.001 s`，同时回带空档区间。
- 所有比较在**整数 timescale 刻度**上进行（与 dash.js 一样先做 15 位有效数字舍入再 `Math.round`），避免浮点误差把边界片算错。
- 负 `@r` 的重复次数沿用 dash.js 公式 `max(ceil((end-start)/d)-1, 0)`，因此最后重复片的终点与下一段起点严丝合缝。
- `序号` = 从零开始的片下标（等同 dash.js 的 `segment.index`）；`编号` = `startNumber + 序号`（即 `$Number$`）；`$Time$` 取该片在清单里的 `@t`（重复段首片用显式 `@t`，后续片用推算时间）。
- 页面与 Node 都只 import `src/lab.js` 这一份逻辑，不存在两套实现；`legacy-scan.js` 是旧逻辑的对照物，生产路径不使用。
